Расширение возможностей ИИ с помощью собственных MCP-серверов · Урок 15 из 19

Интеграция с реальным агентом

Проект~22 мин чтения Репозиторий: build-your-own-mcp-fastmcp

⌨️ В этом практическом задании вы выставите свой сервер Log Triage перед настоящими хостами агентов: по HTTP с bearer-токенами, с различением вызывающих и с промптом, который задаёт рамки расследования.

Log Triage — это MCP-сервер, который позволяет ИИ-агенту разбирать набор логов на вашей машине. Агент спрашивает, какие там есть файлы, что пошло не так в файле или папке за некоторое время и какие строки подходят под шаблон, а в ответ получает счётчики, группы сообщений и несколько строк вместо целых файлов. Сервер умеет читать форматы логов и больше ничего: все выводы делает агент.

Ваш сервер в solution/ уже перечисляет, обобщает и ищет логи, хранит сканирования, по которым агент может листать, читает вокруг строки, проверяет каждый путь, пишет в лог каждый вызов и рисует временную шкалу, а ваши тесты и проба его проверяют. Пока что он работает только как процесс, который запускает хост вашего агента, для одного вызывающего.

Марта дежурит на платформе хостинга, и её агент для программирования отвечает на вопросы о логах через сервер, до которого её команда хочет достучаться из собственных хостов агентов: у каждого свой токен, а один из токенов только для чтения. Прежде чем передать сервер, она хочет увидеть его так, как его показывают хосты, и задать ему два настоящих вопроса.

В конце ваш агент отвечает на вопросы о логах через хост. Два вопроса обязательны, слово в слово:

Customers got errors on the invoices page late in the morning of 2026-09-09. Which instance, when, and why?

The API logs say 'DB is locked'. Since when, how often, is it getting worse, and what does the database say?

В cases.md в папке практики они приведены с подсказкой, где искать, плюс два необязательных вопроса.

Что вы строите:

  • Флаг --http HOST:PORT: streamable HTTP без состояния на /mcp, с bearer-токенами из LOG_TRIAGE_TOKENS, ответом 401 для отсутствующего или неизвестного токена и 403 для чужого Origin.
  • Вызывающих по токенам: каждое сканирование принадлежит своему вызывающему, а вызывающий только для чтения не видит save_finding и получает E13, если вызовет его.
  • Промпт triage, последнее предложение в instructions и версию 0.4.0.
  • Две регистрации в хостах, выводы по кейсам и заметки о том, что показали хосты.

Stdio остаётся по умолчанию, с единственным вызывающим local, поэтому уже имеющиеся проверки продолжают проходить. CLAUDE.md в папке практики говорит вашему агенту то же самое.

Вам нужно знать, как MCP-сервер обслуживается по HTTP и от чего защищает проверка Origin, что такое bearer-токен и principal, как хост агента регистрирует сервер и спрашивает разрешение перед запуском инструмента.

2. Задача 1: HTTP с токенами

💡 Цель: обслуживать сервер по HTTP только для вызывающих с известным bearer-токеном и допустимым локальным Origin либо без заголовка Origin.

FastMCP обслуживает /mcp по HTTP, когда сервер запущен с transport="http" и stateless_http=True. Проверка Origin выполняется первой, проверка учётных данных — второй, так что отклонённый запрос никогда не доходит до инструмента.

Реализуйте правила HTTP из разделов 1 и 7 файла 4-agents-and-clients/CONTRACT.md:

  • Добавьте --http HOST:PORT, чтобы обслуживать /mcp в режиме без состояния. Stdio остаётся по умолчанию.
  • Читайте LOG_TRIAGE_TOKENS как записи через запятую вида token=principal или token=principal:read-only. Если HTTP включён, а переменной нет, завершитесь с кодом 2 и выведите в stderr LOG_TRIAGE_TOKENS is required with --http.
  • Принимайте запрос без Origin либо с заголовком, равным ровно http://localhost или http://127.0.0.1 с необязательным портом. Любой другой origin отклоняйте с 403 до проверки токена. Затем требуйте известный bearer-токен, иначе возвращайте 401 с WWW-Authenticate: Bearer.
  • В этой задаче оставляйте аутентифицированного вызывающего как local. Держите stdout пустым по HTTP, свои строки HTTP-сервера отправляйте в stderr или отключите, а команду запуска по HTTP добавьте в solution/README.md.
Подсказки
  1. Оставьте stdio путём по умолчанию. Флаг --http выбирает второй транспорт.
  2. Выполняйте проверку Origin до разбора токена, чтобы чужая страница не могла узнать, действителен ли токен.
  3. Поместите проверки Origin и bearer-токена в ASGI middleware вокруг одного HTTP-приложения FastMCP.
Промпт
Add streamable HTTP to the server in solution/, as 4-agents-and-clients/CONTRACT.md sections 1
and 7 describe it: a --http HOST:PORT flag in __main__.py, stateless HTTP at /mcp set up in a
new src/logtriage/http.py, and the bearer tokens from LOG_TRIAGE_TOKENS and the Origin check
in a new src/logtriage/auth.py. Stdio stays the default and doesn't change. With --http,
nothing may reach stdout, the HTTP server's own lines included. Every caller is still local
for now. Add the HTTP command to solution/README.md.

CLAUDE.md в папке практики просит оставить host_origin_protection в FastMCP выключенным, как по умолчанию, потому что он пропускает больше origin, чем разрешает контракт, и проверять Origin в ASGI middleware, которое видит каждый запрос раньше, чем FastMCP ответит 401 на маршруте /mcp. uvicorn, HTTP-сервер под FastMCP, пишет свои access-строки в stdout, пока ему не дали собственную конфигурацию логирования, так что отправьте их в stderr или отключите.

3. Задача 2: вызывающие

💡 Цель: держать сканирования каждого вызывающего приватными и не давать вызывающему только для чтения записывать.

При stateless_http=True каждый запрос обслуживается одним объектом FastMCP. Сканирование переходит между запросами через свой scan_id и общее хранилище, которое на каждом запросе сверяет этот id с вызывающим.

Реализуйте правила для вызывающих из разделов 4, 6 и 7 файла 4-agents-and-clients/CONTRACT.md:

  • Читайте principal токена на каждом HTTP-запросе и оставляйте local по stdio. Авторизуйте каждое чтение и запись сканирования по этому principal. Два токена одного principal делят сканирования. Другой principal получает E6 от инструмента или resource-not-found от triage://scans/{scan_id}.
  • Сделайте общее хранилище безопасным для параллельных запросов и применяйте лимит в 20 сканирований отдельно к каждому вызывающему.
  • Скрывайте save_finding из tools/list вызывающего только для чтения. Корректный прямой вызов возвращает E13, save_finding is not available to this caller. Глобальный --read-only по-прежнему убирает инструмент для всех. Помечайте tools/list значением cacheScope: "private".
  • Добавьте собственные HTTP-тесты для общих и раздельных principal и для вызывающего только для чтения.
Подсказки
  1. Определяйте вызывающего по access token FastMCP на границе запроса и передавайте его в каждый обработчик с состоянием.
  2. Держите одно хранилище сканирований на все HTTP-запросы без состояния. Транспорт без состояния не означает пустое состояние приложения.
  3. Используйте middleware и для фильтрации tools/list, и для отказа на прямой вызов save_finding с E13.
Промпт
Make the caller come from the bearer token, as 4-agents-and-clients/CONTRACT.md section 7
(Callers) says: the scan store in scans.py keeps each scan for its caller, local over stdio
and the token's principal over HTTP, and every tool and resource that reads a scan reads it
as that caller. A read-only principal doesn't see save_finding in tools/list and gets E13
when it calls it: add E13 to errors.py and the rest to tools/findings.py. --read-only still
removes the tool for everyone. Add tests of your own for two callers over HTTP.
Run from the repository root: uv run --project solution pytest solution/tests, then
uv run --project 4-agents-and-clients/checks pytest 4-agents-and-clients/checks
Checkpoint: test_t1_http.py and test_t2_principals.py pass; test_t3_prompt.py still fails;
the practice 1 to 3 checks still pass.

Хранилище сканирований одно на весь процесс, и каждый инструмент читает и сохраняет сканирования от имени вызывающего, которого называет get_access_token() из FastMCP, а при отсутствии токена это local. Если скрывать save_finding через auth=require_scopes(...), вызов вызывающего только для чтения получил бы отказ FastMCP «неизвестный инструмент», а не E13, так что скрытие и E13 — это ваш собственный код, например FastMCP middleware, которое выполняется до того, как FastMCP проверит аргументы, и поэтому отвечает E13 даже на неверные.

4. Задача 3: промпт triage

💡 Цель: опубликовать промпт, который задаёт рамки расследования агенту, ничего не знающему об этих логах.

Промпт — это примитив, который запускает пользователь. @mcp.prompt публикует его с аргументами, у которых есть имя, описание и признак обязательности, но нет типа.

Постройте triage по правилам из раздела 5 файла 4-agents-and-clients/CONTRACT.md:

  • Зарегистрируйте обязательный symptom, затем необязательные path, since и until, именно в таком порядке. Дайте описание промпту и каждому аргументу. Пустой или отсутствующий path означает весь корень логов.

5. Задача 4: два хоста

💡 Цель: подключить HTTP-сервер к двум настоящим хостам агентов, у каждого свой токен.

Когда в хосте зарегистрирован ваш сервер, он подключается и обнаруживает ваши инструменты. Запустите Claude Code с --permission-mode default и через /permissions удалите все сохранённые правила allow, которые покрывают mcp__log-triage__save_finding. Инструменты чтения одобряйте по мере необходимости, а сохранения — по одному, чтобы проверять их аргументы. Codex CLI с настройкой одобрения writes из hosts.md спрашивает перед инструментом, не помеченным как только для чтения.

Следуйте hosts.md: запустите сервер по HTTP с примерами токенов, зарегистрируйте его в Claude Code с --scope project и в Codex CLI и работайте в каждом хосте так, как сказано в его разделе Use, включая сессию viewer.

Если в одном из хостов уже есть запись с неверной командой или URL, выполните только подходящую команду удаления, а затем повторите регистрацию из hosts.md:

bash
# Run from the repository root. For Claude Code, use the scope containing the wrong entry.
claude mcp remove log-triage --scope local
claude mcp remove log-triage --scope project
codex mcp remove log-triage

--scope project оставляет регистрацию Claude Code в .mcp.json в корне репозитория. Команда claude mcp add в hosts.md берёт заголовок Authorization в одинарные кавычки, которые сохраняют ${LOG_TRIAGE_TOKEN} как написано. Claude Code читает эту переменную при подключении, а сервер читает LOG_TRIAGE_TOKENS.

Подсказки
  1. Держите токен в переменной окружения. Не вставляйте его значение в файлы проекта.
  2. Регистрируйте Claude Code в области проекта, чтобы .mcp.json оставался локальным для этого репозитория.
  3. Сравните списки инструментов analyst и viewer, прежде чем проверять одобрение записи.

Проверка:

  • claude mcp get log-triage показывает область Project и ⏸ Pending approval, пока вы не одобрите регистрацию.
  • В Claude Code /mcp показывает log-triage подключённым с семью инструментами. С токеном viewer — шесть, без save_finding.
  • В Codex CLI /mcp показывает те же семь инструментов.
  • Когда агент хочет выполнить save_finding, хост сначала спрашивает вас.

6. Задача 5: кейсы

💡 Цель: ответить на настоящие вопросы через хост, используя свой промпт, чтобы задать рамки каждому расследованию.

Когда агент ошибается, хост мало что говорит о причине, поэтому менять приходится на стороне сервера: описание инструмента или instructions, которые модель читает перед вызовом.

Подсказки
  1. Начинайте новую сессию хоста для каждой попытки, чтобы единственным изменившимся входом были исправленные описания и instructions.
  2. Проверяйте процитированные строки источника, прежде чем одобрить save_finding.
  3. Читайте каждый новый файл отчёта до коммита. У сервера намеренно нет инструмента удаления.

Два обязательных вопроса, слово в слово, с подсказкой, где искать:

Customers got errors on the invoices page late in the morning of 2026-09-09. Which instance, when, and why?

Где искать: pods.

The API logs say 'DB is locked'. Since when, how often, is it getting worse, and what does the database say?

Где искать: весь корень логов.

Команда промпта на шаге 2 запускает расследование сразу после отправки, и агент может попытаться сохранить вывод ещё до вашего вопроса: остановить его можно на шаге разрешений хоста. Агент также может записать доказательства прямо в summary, увидеть отказ при сохранении, принять инструмент за сломанный и сохранить тестовые выводы, так что прочитайте всё в reports/ перед коммитом: у сервера нет инструмента, который удаляет выводы.

Для каждого обязательного вопроса из cases.md:

  1. Начните новую сессию Claude Code, в которой есть только инструменты вашего сервера: claude --tools "". --tools "" убирает встроенные инструменты Claude Code, но не другие MCP-серверы, которые вы добавили. Если /mcp показывает что-то кроме log-triage, отключите это там для данного проекта, а когда закончите, включите обратно тем же способом.
  2. Запустите промпт с симптомом в одно слово, местом поиска и, если вопрос называет время, с окном, прочитанным из слов самого вопроса. Для первого вопроса, например, «late in the morning of 2026-09-09»: /mcp__log-triage__triage invoice-errors pods 2026-09-09T09:00 2026-09-09T13:00. Claude Code делит аргументы по пробелам, поэтому симптом из нескольких слов расползётся по другим аргументам.
  3. Когда агент ответил на промпт, задайте вопрос из cases.md слово в слово.
  4. Прежде чем доверять ответу, проверьте, что его источники согласуются по времени: сравните даты в первых строках каждого процитированного файла с датой в имени этого файла, а также время одного события в двух разных логах.
  5. Когда ответ есть, попросите сохранить вывод и прочитайте, что агент собирается записать, прежде чем разрешить.
  6. Прочитайте новый файл в reports/ и сверьте его с разделом «A good finding» в cases.md, а затем отметьте пункты кейсов в CHECKLIST.md.

Хороший вывод, как его формулирует cases.md:

  • Он отвечает на каждую часть вопроса, в порядке вопроса.
  • Каждое утверждение опирается на строку, которую вывод цитирует по файлу и номеру строки, и каждая процитированная строка говорит то, что вывод ей приписывает.
  • Время указано в UTC, а где два источника расходятся по времени, вывод говорит, какому из них он доверяет и почему.
  • Он говорит, чего логи не показывают, а не гадает.
  • То, что происходит каждый день, названо один раз как фон, а не как причина.

Если агент выбрал не тот инструмент, потратил несколько вызовов на поиск местонахождения файла или упустил часть вопроса, улучшите описание инструмента или instructions, перезапустите сервер и спросите снова в новой сессии. Запишите, что вы изменили, в CHECKLIST.md.

Два необязательных вопроса работают так же. Когда закончите, сделайте коммит reports/.

Проверка: по каждому обязательному вопросу в reports/ есть вывод, соответствующий «A good finding» из cases.md, а CHECKLIST.md фиксирует все изменения описаний, которые вы сделали.

7. Задача 6: что показывает хост

💡 Цель: понаблюдать за сервером через хост и определить одно улучшение на стороне сервера для каждого трудного взаимодействия.

Хост мало что показывает, когда вызов медленный, оборван или отклонён, и каждый из этих случаев указывает на то, чем управляет ваш сервер: сколько длится работа, какой счётчик и какую заметку вы кладёте в ответ и что вызывающему разрешено видеть.

Подсказки
  1. Записывайте результат, который показал хост, отдельно от диагностики в терминале сервера.
  2. Отличайте отказ в одобрении от отказа сервера. Они происходят на разных границах.
  3. Если результат обрезан, проверьте, хватило ли счётчика и заметки о постраничной выдаче в ответе, чтобы агент мог продолжить.

В сессии Claude Code с вашим сервером попробуйте каждое из этого и запишите в CHECKLIST.md, что показал хост и какое одно изменение мог бы сделать сервер:

  • Медленный вызов: попросите summary по всему корню логов без окна. Как долго хост ждёт и что показывает в это время?
  • Обрезанный ответ: попросите поиск, который находит тысячи строк. Замечает ли агент заметку о постраничной выдаче и просит ли ещё, или отвечает по первой странице?
  • Отклонённое сохранение: попросите агента сохранить вывод и откажите в разрешении. Что он делает дальше? Затем начните сессию с токеном viewer и спросите снова: что он говорит, когда save_finding нет?
  • Аргументы промпта: запустите промпт с симптомом из нескольких слов в кавычках. Что промпт повторяет в ответ?
  • Запрос без токена: начните сессию с неустановленным LOG_TRIAGE_TOKEN. Что показывает хост и что показывает терминал вашего сервера?

Проверка: в таблице «What the host showed» в CHECKLIST.md есть строка для каждой попытки.

8. Задача 7: проверка в MCP Inspector

💡 Цель: с помощью MCP Inspector проверить проверку токена без агента между клиентом и сервером.

Запуск Inspector напрямую показывает проверки транспорта. У каждого токена свой список инструментов, а запрос без токена получает 401 до запуска любого инструмента.

Здесь используйте пакет Inspector напрямую. fastmcp dev inspector запускает голую команду fastmcp run без этой HTTP-конфигурации, поэтому не может выбрать современную эру протокола, нужную для проверки метаданных вроде cacheScope.

Подсказки
  1. Держите сервер запущенным в отдельном терминале, прежде чем вызывать CLI Inspector.
  2. Используйте --stored-auth-only для записи без токена, чтобы Inspector сообщил о 401, а не начал OAuth.
  3. Сравните два ответа tools/list, прежде чем отрисовывать промпт с симптомом из нескольких слов.

В inspector.json в папке практики три HTTP-записи для сервера на 127.0.0.1:8765: log-triage-http отправляет первый пример токена, log-triage-http-viewer — токен только для чтения, а log-triage-http-no-token не отправляет ничего. В каждой задано "protocolEra": "modern", из-за чего Inspector использует протокол 2026-07-28. Запустив сервер, как в задаче 1, выполните этот блок из 4-agents-and-clients/:

bash
# Run from 4-agents-and-clients/.
npx @modelcontextprotocol/inspector --cli --config inspector.json --server log-triage-http --method tools/list --format json
npx @modelcontextprotocol/inspector --cli --config inspector.json --server log-triage-http-viewer --method tools/list --format json
npx @modelcontextprotocol/inspector --cli --config inspector.json --server log-triage-http-no-token --stored-auth-only --method tools/list --format json

Первая команда показывает семь инструментов. Вторая — шесть, без save_finding. Третья пишет ответ в stderr, ничего не пишет в stdout, завершается с кодом 3 и выводит:

{"error":{"code":"auth_required","message":"Version negotiation failed: the server requires authorization (HTTP 401)"}}

Без --stored-auth-only Inspector пытается начать вход через OAuth и сообщает, что ему нужен терминал. Уведомления npm — это диагностика CLI, они могут появляться вокруг вывода протокола. Терминал сервера показывает access-строку на каждый запрос, если вы не отключили access-лог uvicorn.

Затем отрисуйте промпт с симптомом из нескольких слов, который Inspector передаёт целиком. Выполните эту команду из 4-agents-and-clients/:

bash
# Run from 4-agents-and-clients/.
npx @modelcontextprotocol/inspector --cli --config inspector.json --server log-triage-http --method prompts/get --prompt-name triage --prompt-args "symptom=pages time out" path=pods --format json

Проверка: запись analyst показывает семь инструментов, запись viewer — шесть, запись без токена сообщает о HTTP 401 без запуска OAuth, а triage повторяет pages time out как одно значение.
