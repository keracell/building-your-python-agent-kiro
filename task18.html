Подключаем телеметрию для MCP

Проект~27 мин чтения Репозиторий: build-your-own-mcp-fastmcp

⌨️ В этом практическом задании вы добавите трассы OpenTelemetry в свой сервер Log Triage и по ним увидите, на что расход времени сервера уходит в ходе расследования.

Log Triage — это MCP-сервер, с помощью которого ИИ-агент расследует набор логов на вашей машине. Агент спрашивает, какие там есть файлы, что пошло не так в файле или папке за некоторый промежуток времени и какие строки соответствуют шаблону, а в ответ получает счётчики, группы сообщений и несколько строк вместо целых файлов. Сервер умеет читать форматы логов и больше ничего: все выводы делает агент.

Ваш сервер в solution/ уже перечисляет, суммирует и ищет по логам, хранит сканы, по которым агент может листать страницы, читает вокруг строки, проверяет каждый путь, пишет лог каждого вызова, рисует временную шкалу и обслуживает несколько вызывающих сторон по HTTP с промптом, задающим рамки расследования. Он отвечает, но ничто не фиксирует, сколько времени занял ответ и какая работа за ним стояла.

Марта дежурит по хостинг-платформе своей команды, и её кодинг-агент отвечает на вопросы о логах платформы через сервер, к которому команда теперь обращается по HTTP. Один ответ пришёл верным, но слишком долго, и, прежде чем менять код, она хочет понять, какой из стоящих за ним вызовов занял больше всего времени и какая часть времени этого вызова ушла на чтение логов.

В конце ваш агент отвечает на вопрос о логах при включённой телеметрии, а вы читаете по трассе, во что обошлось его расследование. Обязательный вопрос, слово в слово:

Certificate orders were failing at some point. When did it start, is it still happening, and do the CI results agree?

Что вы построите:

  • Версию 0.5.0 с теми же инструментами, ресурсами и промптом.
  • Необязательный экспорт по OTLP/HTTP из стандартных переменных OTEL_, с именем и версией сервиса и ограниченным по времени сбросом перед выходом сервера, из готового модуля, который вы подключите.
  • Один SERVER-спан на запрос, названный по конвенциям MCP и присоединённый к трассе вызывающей стороны из _meta, с trace ID в отладочной строке tool=.
  • Спаны чтения по каждому файлу со счётчиками выполненной работы.
  • Спаны без аргументов, результатов, отклонённых URI ресурсов и токенов.
  • Один вызов инструмента в LangSmith как tool run с его read runs, а в локальном просмотрщике трасс — со счётчиками.
  • Трассированное расследование и ответы на два вопроса по его трассе.

Если endpoint не задан, ничего не экспортируется, а сервер ведёт себя как сейчас. То же самое сказано в 5-telemetry/CONTRACT.md, который агент читает первым по CLAUDE.md практической папки.

Вам нужно знать, что такое спан, трасса и родитель спана, как middleware в FastMCP оборачивает MCP-запрос, как контекст трассировки W3C передаётся в _meta и что OTLP-экспортёр делает с завершёнными спанами.

2. Задача 1: экспорт и завершение работы

💡 Цель: телеметрия выключена, пока не задан endpoint, а если он задан, завершённые спаны доходят до бэкенда раньше, чем сервер завершится.

OTLP/HTTP-экспортёр берёт endpoint и заголовки из переменных OTEL_, а пакетный провайдер держит завершённые спаны в памяти, поэтому сервер устанавливает провайдер до загрузки, только когда endpoint задан, и сбрасывает его перед выходом процесса, в том числе по сигналу. Эта настройка лежит в стартовом модуле 5-telemetry/starter/telemetry.py: configure устанавливает провайдер и экспортёр, когда endpoint задан, shutdown сбрасывает последние спаны не дольше пяти секунд, а flush_and_exit сбрасывает и сразу завершает процесс. Агент подключает его к серверу.

Реализуйте правила из 5-telemetry/CONTRACT.md, раздел Export and lifetime:

  • Скопируйте 5-telemetry/starter/telemetry.py в solution/src/logtriage/telemetry.py, не меняя его код, добавьте в проект сервера OpenTelemetry Python SDK 1.44.0 и его OTLP/HTTP-экспортёр и установите версию 0.5.0.
  • Вызывайте configure до создания сервера. Если не задана ни OTEL_EXPORTER_OTLP_ENDPOINT, ни OTEL_EXPORTER_OTLP_TRACES_ENDPOINT, он ничего не устанавливает и не делает телеметрических запросов, а stdio работает как раньше.
  • Сбрасывайте спаны при любом выходе: EOF на stdin, SIGINT и SIGTERM, по stdio и по HTTP. shutdown сбрасывает после того, как сервер вернул управление, а flush_and_exit — обработчик сигнала для stdio.
  • Добавьте собственный тест жизненного цикла с in-memory-экспортёром или локальным приёмником.
Подсказки
  1. По stdio поток ждёт на stdin, и после сигнала обычный выход ждёт этот поток. Поэтому flush_and_exit сразу завершает процесс после сброса.
  2. По HTTP uvicorn завершается по SIGINT и SIGTERM и затем снова поднимает сигнал. От обработчика, который вы поставили до его запуска, зависит, выполнится ли сброс после этого.
  3. ConsoleSpanExporter из SDK пишет в stdout, а он по stdio принадлежит сообщениям MCP.
Промпт
Read the root agent rules and 5-telemetry/AGENTS.md, README.md and CONTRACT.md. Continue the existing server in solution/.

Copy 5-telemetry/starter/telemetry.py to solution/src/logtriage/telemetry.py without changing its code, and add the OpenTelemetry Python SDK 1.44.0 with its OTLP/HTTP protobuf exporter to the project. Set the version to 0.5.0. Call configure before the server is created, and flush on stdin EOF and on SIGINT and SIGTERM over stdio and HTTP with shutdown or flush_and_exit. Keep stdout protocol-only. Write your own lifecycle test. Do not instrument requests or log reads yet.

Checkpoint: the server's own tests and uv run --project 5-telemetry/checks pytest 5-telemetry/checks -k t1 pass: FastMCP's own request spans are enough for the T1 checks until task 2 replaces them. Commit as "practice 5 task 1: wire in telemetry export" and report the exact checks run.

3. Задача 2: спаны запросов и трасса вызывающей стороны

💡 Цель: каждый MCP-запрос порождает один SERVER-спан с именем по конвенциям MCP, внутри трассы вызывающей стороны, если её несёт _meta, а его статус согласуется с результатом.

Собственный спан запроса FastMCP кладёт текст отказа в описание статуса и в событие исключения, а имя берёт из любого инструмента, который запросит вызывающая сторона, зарегистрирован он или нет. Поэтому сервер переключает FastMCP в propagation_only и открывает SERVER-спан в middleware, добавленном первым, который выполняет всё остальное внутри этого спана. В этом режиме FastMCP по-прежнему читает traceparent и tracestate из _meta и делает спан вызывающей стороны текущим до запуска любого middleware, так что спан, который открывает ваше middleware, становится его дочерним.

Реализуйте правила из 5-telemetry/CONTRACT.md, разделы Request spans и Context and caller:

  • Установите в сервере режим телеметрии FastMCP propagation_only.
  • Один SERVER-спан на каждый обработанный запрос, ни одного на уведомления. Называйте его tools/call <tool> или prompts/get <prompt>, если сервер зарегистрировал такое имя, и просто методом в остальных случаях.
  • Задайте атрибуты из таблицы контракта: mcp.method.name всегда, gen_ai.tool.name и gen_ai.operation.name со значением execute_tool при вызове инструмента, gen_ai.prompt.name для промпта, mcp.resource.uri после успешного чтения ресурса.
  • Результат с isError: true получает статус ERROR и error.type, равный tool_error. Ошибка JSON-RPC получает свой код как error.type, кроме ошибок запроса, которые перечисляет контракт. У успеха error.type нет.
  • Оставьте описание статуса пустым или кладите туда только дополнительные подробности, не содержащие ввода вызывающей стороны: error.type уже называет сбой, а текст отказа может повторять путь или ID скана, присланные вызывающей стороной.
  • На уровне debug при включённой телеметрии добавьте в строку tool= значение trace_id= и 32 шестнадцатеричные цифры трассы. Без телеметрии строка остаётся прежней.
  • Сделайте строковые значения traceparent и tracestate из params._meta родителем спана запроса, по stdio и по HTTP. Их извлекает режим propagation_only в FastMCP. HTTP-заголовки трассировки не читайте.
  • Если корректного контекста нет, начните новую трассу. Если родитель не семплирован, передайте контекст дальше и ничего не записывайте.
  • Запрос без params или без _meta обрабатывается как раньше.
  • Держите аутентифицированного вызывающего в контексте и не кладите состояние трассы в сохранённые сканы: два запроса с одним scan_id — это две трассы.
Подсказки
  1. Отказ доходит до on_request как исключение, а в результат с isError его превращает FastMCP уже после возврата из middleware: ToolError, NotFoundError для неизвестного инструмента, ValidationError для отказа по схеме. NotFoundError не является FastMCPError. Здесь все три дают tool_error, хотя по конвенциям вызов неизвестного инструмента сбоем не считается. На отсутствующие аргументы промпта FastMCP отвечает -32603, кодом внутренней ошибки, хотя ошибку допустила вызывающая сторона. Считайте этот -32603 вместе с ошибками запроса.
  2. FastMCP запускает middleware в том порядке, в каком вы их добавили. От порядка зависит, выполняются ли логгер и инструменты внутри спана запроса.
  3. Запрос без params приходит в on_request обычным словарём, а имя инструмента или промпта может прийти не строкой. Читайте имя инструмента или промпта, только если это строка.
  4. В режиме propagation_only собственный get_tracer() из FastMCP возвращает трассировщик, который ничего не записывает. Открывайте свои спаны трассировщиком из trace.get_tracer OpenTelemetry в текущем контексте, куда FastMCP уже положил спан вызывающей стороны. start_as_current_span этого трассировщика по умолчанию записывает событие исключения и описание статуса из текста исключения. Выключите и то и другое через record_exception=False и set_status_on_exception=False.
  5. Собственный клиент FastMCP заменяет traceparent, который ваш тест кладёт в _meta, своим. Проверяйте контекст через сырой JSON-RPC, например отправляя запросы в http_app() сервера через httpx2.ASGITransport, который MCP SDK уже устанавливает.
Промпт
Follow 5-telemetry/CONTRACT.md's request-span, logging and context rules. Switch FastMCP to its propagation_only telemetry mode, so it opens no request spans of its own, and add FastMCP middleware that creates one SERVER span per dispatched request, skips notifications, names registered tools and prompts safely, and records the required attributes. 4. Задача 3: чтение

💡 Цель: трасса вызова инструмента показывает каждый прочитанный им файл и работу, которую выполнило каждое чтение.

Работа внутри запроса превращается в дочерние INTERNAL-спаны с атрибутами под вашим собственным префиксом, чтобы у медленной части вызова было имя.

Реализуйте правила из 5-telemetry/CONTRACT.md, раздел Read spans:

  • Один INTERNAL-спан logtriage.read на каждый открытый ридер распакованных данных, завершаемый при закрытии этого ридера. Считаются определение формата, обычные чтения, повторные чтения сохранённых сканов и проверка свидетельств в save_finding. Отклонённый путь ничего не открывает и read-спана не имеет.
  • logtriage.files, logtriage.bytes и logtriage.lines в том виде, как их определяет контракт: потреблённая работа, включая определение формата и упреждающее чтение.
  • Продолжайте обрабатывать по одному файлу за раз и не пускайте пути файлов и содержимое ни в один спан.
Подсказки
  1. Считайте байты после распаковки gzip и до декодирования текста или обрезки. Размер сжатых данных отвечает на другой вопрос.
  2. Ридер берёт по 64 КиБ за раз, поэтому чтение при определении формата возвращает больше байтов, чем строк, на которые оно смотрит. Эти байты — тоже работа.
  3. Генератор, читающий файл, закрывает свой ридер, когда исчерпан или отброшен. Откройте read-спан через start_span и завершите его при закрытии ридера, а не делайте его текущим поперёк yield.

5. Задача 4: что не должно попадать в спаны

💡 Цель: экспортируемые спаны объясняют сбои, не неся ввод вызывающей стороны, результат или учётные данные.

Аргументы и результаты — это атрибуты по желанию, а токен на спан не попадает никогда, поэтому экспортируемая запись несёт имена, идентификаторы и счётчики.

Реализуйте правила из 5-telemetry/CONTRACT.md, раздел Privacy:

  • Проверяйте всю экспортируемую запись: ресурс, атрибуты, события и описания статусов.
  • По HTTP задавайте enduser.id — атрибут OpenTelemetry для аутентифицированного пользователя — равным принципалу. Никогда не копируйте bearer-токен или заголовок Authorization.
  • Записывайте URI ресурса, только если чтение прошло успешно. URI, который сервер отклонил, остаётся снаружи, какой бы вид он ни имел.
  • Скрытые ошибки MCP остаются скрытыми. Необязательное событие исключения несёт фиксированное описание, а не сырую ошибку. Это строже, чем позволить спану сбоя нести своё исключение для тех, кто читает трассы, потому что ошибка Log Triage может повторять путь или ID скана, присланные вызывающей стороной, а значения аргументов в спаны не попадают.
  • Проверьте с пишущей стороной и вызывающим только для чтения, а также с неожиданным сбоем из-за недоступной для записи папки отчётов.
Подсказки
  1. Сообщение об отказе может повторять путь или ID скана, присланные вызывающей стороной. Копирование его в описание статуса сводит на нет аккуратный список атрибутов.
  2. У событий исключений есть собственные поля. Проверяйте и их, а не только атрибуты спана.
  3. Тестируйте с выдуманными маркерами, которые легко узнать, а потом ищите их во всём захваченном экспорте. Настоящие секреты в тестовые данные не кладите.
  4. По HTTP MCP SDK перед tools/call с аргументами шлёт вашему серверу собственный tools/list, чтобы сверить заголовки вызова со схемой инструмента. Он приходит с заголовком вызова Mcp-Method: tools/call: спан для него не открывайте.
Промпт
Verify the full exported payload against 5-telemetry/CONTRACT.md's privacy rules: safe protocol metadata and counts only, no arbitrary arguments, results, raw input-bearing errors, bearer tokens, Authorization values or OTLP credentials. Check attributes, events and status descriptions. Keep masked MCP errors unchanged. Record the authenticated HTTP principal as enduser.id, not the token. Add tests for writer/read-only callers and unexpected failures, fixing any leaks without weakening existing path or ownership checks.

Checkpoint: uv run --project 5-telemetry/checks pytest 5-telemetry/checks passes, as do the server's own tests. Commit as "practice 5 task 4: verify telemetry privacy" and report the exact checks run.

6. Задача 5: бэкенд для трасс

💡 Цель: настоящий вызов инструмента появляется в LangSmith как tool run с его read runs, а в локальном просмотрщике — со своими счётчиками.

Экспортёр отправляет данные в один endpoint, а LangSmith отбрасывает атрибуты спанов, которые не сопоставляет, поэтому дерево запусков берётся из LangSmith, а счётчики и типы ошибок — из локального просмотрщика.

Терминалы A и B работают в корне репозитория: A — для локального просмотрщика, B — для сервера, а терминал C работает в 5-telemetry/ для Inspector.

LangSmith

Создайте аккаунт LangSmith и API-ключ в настройках API Keys: оставьте тип Personal Access Token и выберите срок действия. Endpoint ниже использует американский хост api.smith.langchain.com: аккаунту в европейском регионе нужен eu.api.smith.langchain.com.

Ключ — это пароль от вашего аккаунта LangSmith, поэтому храните его там, где хранят пароли, — в хранилище учётных данных системы: в Keychain на macOS, в связке ключей рабочего стола на Linux, а в Windows — в SecretStore, зашифрованном файле-хранилище для вашего пользователя, которым управляет PowerShell. Файл .env хранил бы ключ открытым текстом в одном git add от коммита. Сохраните ключ один раз:

bash
# Run once, in any terminal.
# macOS: your login Keychain; asks twice and shows nothing
security add-generic-password -a "$USER" -s langsmith-api-key -w

# Linux: your desktop keyring; asks once and shows nothing
secret-tool store --label=langsmith-api-key service langsmith-api-key account "$USER"

# Windows (PowerShell): install PowerShell 7 once, then in a new pwsh window install Microsoft's secret modules, let the vault open without a password and store the key
winget install --id Microsoft.PowerShell --source winget
Install-Module Microsoft.PowerShell.SecretManagement, Microsoft.PowerShell.SecretStore -Scope CurrentUser
Register-SecretVault -Name SecretStore -ModuleName Microsoft.PowerShell.SecretStore -DefaultVault
Set-SecretStoreConfiguration -Authentication None
Set-Secret -Name langsmith-api-key
Проблемы с хранилищем ключей
  • macOS: если в вашей Keychain уже есть элемент langsmith-api-key, команда дважды спросит ключ и остановится с сообщением The specified item already exists in the keychain. Удалите старый элемент командой security delete-generic-password -a "$USER" -s langsmith-api-key, затем сохраните новый ключ.
  • Linux: secret-tool входит в пакет libsecret-tools в Debian и Ubuntu (sudo apt install libsecret-tools) и в libsecret в Fedora, и ему нужна сессия рабочего стола с GNOME Keyring или KWallet, разблокированным при входе.
  • Windows: PowerShell 7 (pwsh, 7.3 или новее) ставится рядом с Windows PowerShell, который идёт в составе Windows, и каждая строка для Windows в этом задании выполняется в нём. Microsoft теперь поддерживает оба модуля секретов только ради исправлений безопасности и критических ошибок. Если SecretStore уже хранит ваш секрет таким образом, выполните только строку Set-Secret.
  • Windows: Set-SecretStoreConfiguration -Authentication None просит подтверждения, затем создаёт зашифрованный файл-хранилище и дважды спрашивает новый пароль к нему. После этого ни одна сессия PowerShell больше не спрашивает пароль, так что новому терминалу хватает одной строки, чтобы загрузить ключ. Документация Microsoft не советует эту настройку для важных секретов, а этот ключ предназначен для бесплатного проекта LangSmith, истекает в выбранную вами дату и удаляется при уборке в конце. Set-Secret затем показывает только звёздочки, пока вы вставляете ключ.

Убедитесь, что ключ сохранён. Проверка печатает stored только если элемент существует, и никогда не печатает сам ключ:

bash
# Run in any terminal.
# macOS
security find-generic-password -a "$USER" -s langsmith-api-key >/dev/null && echo stored

# Linux
secret-tool lookup service langsmith-api-key account "$USER" >/dev/null && echo stored

# Windows (PowerShell)
if (Get-SecretInfo -Name langsmith-api-key) { 'stored' }
stored

У Codex остаются его инструменты оболочки и файлов, поэтому попросите его использовать только инструменты этого сервера и проверьте в транскрипте, нет ли прямого чтения s3_logs/.

Исправление регистрации

Если адрес или имя неверны, выйдите из хоста и удалите только запись упражнения, затем повторите её команду добавления с нужными значениями:

bash
# Run from the repository root, Claude Code registration.
claude mcp remove log-triage-telemetry --scope project
bash
# Run from any folder, Codex registration.
codex mcp remove log-triage-telemetry

Файлы проекта и сохранённые выводы остаются на месте.

Проведите расследование

  1. В Claude Code запустите промпт сервера triage с симптомом из одного слова и местом, где искать: /mcp__log-triage-telemetry__triage certificate-orders pods. Claude Code делит аргументы по пробелам, поэтому симптом из нескольких слов расползётся по другим аргументам. В Codex попросите расследовать pods, используя только инструменты этого сервера.

  2. Когда агент ответил на промпт, задайте вопрос, слово в слово:

    Certificate orders were failing at some point. When did it start, is it still happening, and do the CI results agree?

  3. Прежде чем доверять ответу, проверьте его источники: откройте в файлах не менее трёх процитированных строк и сравните даты в первых строках каждого файла с датой в его имени.

  4. Прочитайте, что агент хочет записать, прежде чем разрешить save_finding. Вывод, который засчитывается, отвечает на вопрос, поэтому если агент сохранил вывод, пока выполнял промпт, или остановился, не сохранив, попросите его сохранить свой вывод.

  5. Сравните этот вывод в reports/ с разделом «A good finding» в 4-agents-and-clients/cases.md.

Необязательный вопрос работает так же, в новой сессии:

The 14:00 CI run on 2026-09-02 had hundreds of errors. Why?

Затем ответьте на вопросы по трассе о расследовании обязательного вопроса и запишите их в 5-telemetry/CHECKLIST.md. В LangSmith отфильтруйте LogTriagePractice по типу запуска tool и времени этой сессии. Для счётчиков перезапустите сервер на локальный просмотрщик, как в задаче 5, и повторите самый долгий вызов через Inspector с его аргументами из транскрипта хоста. Для одних и тех же аргументов счётчики одинаковы.

Вопрос Что записать
Q1 Сколько вызовов инструментов сделало расследование и какой из них занял больше всего времени
Q2 Для этого вызова: его чтения файлов и распакованные байты, а также доля его времени в запусках logtriage.read
Подсказки
  1. Свяжите вопрос с его вызовами инструментов через транскрипт хоста. Спаны сервера не несут ход хоста.
  2. Держите выводы в рамках свидетельств: записанная в логе причина сбоя — это не наблюдаемая первопричина или исправление.
  3. Если хост присылает свой контекст трассировки, родителем становится спан хоста. LangSmith отбрасывает спан, чей родитель до него так и не дошёл, а локальный просмотрщик показывает родителя как внешнего.
  4. Перезапущенный сервер не хранит ни одного скана сессии. Если самый долгий вызов использовал повторно scan_id, сначала повторите вызов summarize_logs, который его создал, а затем самый долгий вызов с новым scan_id.

Проверьте: вывод в reports/ отвечает на каждую часть вопроса с подтверждающими ссылками на файлы и строки, транскрипт показывает в расследовании только инструменты log-triage-telemetry, а Q1 и Q2 называют запуски из вашей сессии.

bash
# Run in each terminal used for the practice.
# macOS and Linux
unset LANGSMITH_API_KEY OTEL_EXPORTER_OTLP_ENDPOINT OTEL_EXPORTER_OTLP_TRACES_ENDPOINT

# Windows (PowerShell)
Remove-Item Env:LANGSMITH_API_KEY, Env:OTEL_EXPORTER_OTLP_ENDPOINT, Env:OTEL_EXPORTER_OTLP_TRACES_ENDPOINT -ErrorAction Ignore
Remove-Item Env:OTEL_EXPORTER_OTLP_HEADERS, Env:OTEL_EXPORTER_OTLP_TRACES_HEADERS, Env:OTEL_SERVICE_NAME -ErrorAction Ignore

bash
# Run in any terminal.
# macOS
security delete-generic-password -a "$USER" -s langsmith-api-key

# Linux
secret-tool clear service langsmith-api-key account "$USER"

# Windows (PowerShell)
Remove-Secret -Name langsmith-api-key -Vault SecretStore
